# Track C operations

Use the administrator Configuration screen for lifecycle and published configuration. Account edits require the displayed version. Changing your own access is blocked; another active administrator must do it. Deactivation first denies database/Storage access and revokes refresh sessions, then bans Auth. If Auth returns an error, refresh the account list and retry the access change; do not report sign-in revocation until the endpoint succeeds. Reactivation requires a fresh sign-in. Erasure requests are retained for review under a retention policy; no automatic deletion or audit-history removal is performed.

Pending invitations are determined from Auth invitation/sign-in timestamps. Resend records an acknowledgement only after Auth accepts the request. Invitation/recovery delivery still requires the separate Supabase SMTP setup in `brevo-staging.md`.

For offline conflicts, open Offline queue, compare local and server data, then choose the explicit reviewed retry or discard. Retry fetches the draft again; another change requires another review. Decisions cannot be overwritten. Retrying one conflict does not delete other queued work. Sign-out warns before purging unsynced local data.

Grievance evidence uses document-wallet uploads and their immutable IDs. The server sets the first owner and category SLA. Officers may assign only within the student's scope. Resolution requires notes. Students can appeal/reopen a resolution; only overdue unresolved cases can escalate to an administrator. The timeline retains earlier messages and changes.

Critical workflow events persist in-app notices and queued email attempts in one transaction. The email worker is `pilot-notifications`, callable by an active administrator; the Notifications screen processes up to ten due attempts per click. Failed/blocked real-send attempts have increasing retry times and stop after five attempts; missing-configuration attempts are excluded from that cap. The five-minute processor is enabled; provider configuration remains deferred. Missing credentials do not claim jobs or consume real-send retries. Do not repeatedly resend uncertain requests: `unknown` or abandoned `processing` jobs need provider-log reconciliation before a deliberate service-side retry. Provider IDs mean acceptance, not inbox delivery. Bounce/delivery webhooks and SMS/IVR are not implemented.

Transactional email requires server-only `BREVO_API_KEY`, `PILOT_EMAIL_SENDER` (verified sender), and the existing HTTPS `PILOT_INVITE_REDIRECT_URL`. The Brevo API key is separate from the SMTP login/key used by Supabase Auth. Set it through Supabase's secrets interface or a private ignored env file using the current CLI help; never through Vite or chat. Leave it unset until sending is authorized. After configuration, use controlled accounts to verify deficiency/sanction/payment queueing, provider acknowledgement, failures and retry handling before closing C5. See [Brevo sending](https://developers.brevo.com/reference/send-transac-email) and [idempotency limits](https://developers.brevo.com/docs/heterogenous-versions-batch-emails).

Scheme editing saves an unpublished draft. Inspect its diff, run the cohort evaluator, then publish. A changed published base makes a stale draft fail. Submission and dry-run share the PostgreSQL rule evaluator. Historical published configurations can be restored as a new version; existing submitted profile/rule snapshots remain intact. Institution activation controls new profile/draft/submission work. Review saved history before reactivating an institution.

Withdrawal is allowed before a decision. Appeal reopens a rejected application only after nodal/admin review, and resets source checks. Renewal creates a new next-year draft after the next scheme year is published; the previous application and its outcome remain. Bulk sanction uses the existing stage/document/source checks per record and returns individual outcomes; retry failures with refreshed versions rather than repeating successful records.

Receipt QR links remain stable through decisions. The public response contains only reference, issue time, current decision hash and validity. Nodal/admin revocation or expiry requires a policy reason and is audited. Hashes identify the current chain; previously copied hashes describe an earlier checkpoint. Public lookup retains the existing shared quota.

Run `npm run test:track-c-staging` only on the dedicated synthetic staging project: it creates additional test fixtures and performs real lifecycle/decision actions without sending mail. `npm run test:track-c-browser` checks its fixture through the hosted UI. `npm run test:browser` tests real IndexedDB/service-worker conflict UI using synthetic HTTP; `npm run test:db` tests real PostgreSQL with Auth/Storage schema fixtures.

For a deployment rollback, keep current database migrations and audit history. Roll back published scheme data through the UI and deploy a reviewed compatible frontend/function revision. For disaster recovery, use the protected database/Auth/private-byte restore procedure in `staging-release.md`; choose a fresh snapshot name, preserve accepted backups and test a separate target. Track B automatic protected backups, alert delivery and malware decision remain open.
